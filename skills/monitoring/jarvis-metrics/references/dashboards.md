# Dashboard Construction and Recipes

Contents: Common construction flow; Choose a practical panel; Derived measures and query modes;
Direct Kusto dashboards: no conversion required; Parameters, mixed sources, and additional
widgets; Copy, import/export, and persistence.

## Common construction flow

Inspect the actual page before acting; do not automate against guessed labels, selectors, or
URLs.

1. Select the requested destination and create a draft, or work on an approved copy. Record the
   original identity before editing an existing dashboard; do not overwrite a shared view.
2. Add a widget suited to the question using the table below, and choose its source explicitly.
   Choosing a widget type does not create telemetry or convert logs to metrics.
3. Configure the layer settings listed in [Build the Dashboard](../SKILL.md#build-the-dashboard),
   plus the preaggregate for an MDM source. Start with one known series.
4. Set units, axes, legend, series names, display reduction, and refresh behavior. Choose the
   reduction on purpose: a summary tile's latest value and a full-window sum are not
   interchangeable. Show the time window and freshness, not just a number.
5. Bind common filters and the time selection to every applicable layer. Test them with at least
   two known values and an empty selection; a parameter control does nothing until it is bound.
6. Reconcile values using [validation](./validation.md), then save to the authorized
   destination. Reopen the saved artifact rather than trusting an unsaved browser view.

## Choose a practical panel

These are report recipes, not a complete list of current Jarvis widget names. Older guides show
graph, line, column, area, sparklines, summary, donut, table/Table V2, text, and heatmap widgets
(not checked against current Jarvis). Check availability and the exact source-to-column mapping
in the picker.

| Report | Candidate display | How to configure and check |
|---|---|---|
| Request/event volume | Line or column | Sum count values per completed time bucket; split only on retained dimensions. Reconcile bucket sums to the source total. |
| Throughput | Line | Divide interval event counts by that interval's seconds; label requests/second. Never apply a derivative to already-per-interval counts. A cumulative counter needs reset-aware deltas. |
| Success/failure percentage | Line plus summary | Use matching success and failure subqueries and the ratio recipe below; label ratio versus percent explicitly. |
| Failure-category breakdown | Column, table, or donut | Sum failed-event counts by bounded reason; use one population/window. A donut is for mutually exclusive parts of a known whole, not overlapping categories. |
| Version/region/environment comparison | Multiple series, column, or table | Bind identical time and non-comparison filters. Show traffic and rate together so changes in mix do not look like regressions. |
| Latency p50/p95/p99 | Line or summary | Select supported percentile sampling on raw/distribution-capable measurements. Confirm units. Percentiles of precomputed percentiles are not request-level percentiles. |
| CPU, memory, capacity, backlog | Line plus latest/max summary | Use appropriate gauge semantics. Sum distinct disjoint capacities only if intended; do not sum repeated time samples of the same gauge. |
| Current KPI/status | Summary | Choose latest, max, or period total deliberately. Include units, measured period, freshness, and explicit unknown/stale state. |
| Fleet trends | Sparklines or table | Keep one stable series per entity/category, consistent units/window, and bounded result count. Inspect exact values alongside trends. |
| Top failing categories | Sorted table or bars | Rank by the defined count/rate and show its denominator. Compute whole-population totals before top-N filtering, not from the truncated table. |
| Distribution or heatmap | Supported heatmap or bucketed table/columns | Supply documented bucket boundaries, frequencies, and time/category axes. Verify conservation of counts; a set of p95 values is not a histogram. |
| Detailed investigation | Direct-Kusto table | Return the necessary columns, bounded rows, explicit time range, and sort order. Minimize sensitive fields; do not pretend a truncated result is complete. |
| Definition/runbook context | Text | Explain units, population, freshness, and approved navigation links without embedding secrets or private details into exported public artifacts. |

## Derived measures and query modes

Use structured or basic metric selection for simple series. Advanced editing can show sublayers,
subqueries, and expressions, and some deployments support KQL-M
(not checked against current Jarvis). KQL-M, Kusto KQL, and the widget's expression language
are not interchangeable. Start from a working query generated by the current editor, use
documented operators, and validate the query there. This bundle does not supply universal MQL or
KQL-M syntax.

For reliability, prepare named success `S` and failure `F` inputs at the same grain, with the
same timestamps, units, population, filters, and aggregation. Then express this logic in the
target editor's syntax:

```text
T = S + F
failure_percent = 100 * F / T, only when T > 0 and both inputs are valid
success_percent = 100 * S / T, under the same conditions
```

If `T = 0`, show "no traffic" or unknown, not 0% failure or 100% success. An absent or stale
input is not a measured zero. If unknown or cancelled outcomes exist, define their denominator
policy and show coverage; `S + F` is the total only for the agreed eligible population. Aggregate
counts first, then divide. Do not average percentages across unequal populations. Joins or
subquery combinations must match all required dimension keys, not just display names.

Multiple independent layers compare metrics without inventing a join. Computed subqueries
combine aligned inputs. Converting display units changes both labels and values; changing a
label alone does not convert milliseconds to seconds.

## Direct Kusto dashboards: no conversion required

1. Select Kusto as the widget source and choose the authorized cluster and database. Check that
   the intended readers can run the query; dashboard access does not grant data access.
2. Run a bounded query over an explicit completed interval. For a time series, return a datetime,
   numeric measures, and the intended series keys. For a table, use explicit columns. For a
   summary, reduce to the scalar or group you want on purpose. Map fields in the editor.
3. Adapt [the synthetic count example](../examples/kusto-counts.kql) for a time series or table.
   Its `d_` and `m_` names show a connector-style shape; direct dashboard queries need those
   prefixes only if the actual widget contract requires them.
4. Bind the dashboard's time and dimension parameters with its documented substitution or
   binding mechanism. Confirm single-value, multi-select, and All behavior and how strings are
   escaped. Do not concatenate arbitrary user text into KQL or invent placeholder syntax.
5. Set row and series limits and refresh cadence for the source's cost and freshness needs.
   Inspect query errors, timeouts, and partial results instead of presenting them as an empty,
   healthy panel. When authorized, reconcile with the same query and window outside the widget.

This creates a query-backed visualization, not an MDM metric or a metric-based alert pipeline.
If the requirement is a durable metric for monitoring, use K2M, L2M, or native emission instead.
An ADX dashboard is an alternative deliverable for exploratory reporting, not a silent
substitute for a requested Jarvis dashboard.

## Parameters, mixed sources, and additional widgets

For each parameter, record its type, allowed values, default, All behavior, and the exact binding
in every layer. A dimension can be fixed, split, aggregated away, or parameterized, and each
answers a different question. Test that excluded environments never leak into a panel.
Coordinate time range and refresh behavior across sources, which may have different delays.

Older guides describe charts that mix MDM and Kusto sources, and incident sources
(not checked against current Jarvis). Confirm support and permissions before combining them.
Time correlation does not prove that an incident caused a metric change, and a missing incident
response does not mean "no incidents."

Older widget pickers also show DGrep Logs, REST API, and XPing Metrics
(not checked against current Jarvis). Treat these as candidates to explore, not guaranteed
integrations. For any additional widget:

1. Check whether it exists in the target, and read its current input and authentication contract.
2. Identify source permissions, output shape, query, time, and refresh limits, and network policy.
3. Build the smallest authorized, non-sensitive preview and inspect actual data and error states.
4. Test parameter binding, empty and stale results, save and reload, and reader access before
   claiming support. If the contract is unavailable, name the blocked capability rather than
   guessing.

Do not install plugins, call arbitrary REST URLs, expose tokens in widget JSON, or promise an
API, export, or report-scheduling feature just because an old screenshot shows a related label.

## Copy, import/export, and persistence

Use saved or copied widgets, or the JSON import and export controls
(not checked against current Jarvis), to reuse approved work. If the target offers Save As or
clone, check the new identity; do not assume a universal clone API. Export a baseline to an
approved private location before changing a shared artifact.

Treat imported JSON and embedded queries and links as untrusted data. Review source
destinations, credentials, sensitive fields, parameters, refresh cost, and external calls before
rendering. Use the target's current export format rather than a made-up JSON schema. Cross-cloud
or cross-version compatibility is not guaranteed.

Save to a new authorized identity first, reopen it, exercise the parameters, and check the query
values and intended reader access. Sharing a dashboard is separate from granting permission to
its backing data. A source-controlled save may only prepare a PR; confirm deployment separately.
